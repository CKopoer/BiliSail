# 架构决策记录

记录日期：2026-10-05。D1–D7 记录初始设计决定；D8 起记录实际实现与验证后的选择。未完成的平台和能力仍不能视为通过验收。

## D1：Flutter UI，优先三个原生平台

**决定**：Android、Windows、macOS 共用 Flutter 页面、领域逻辑与组件；按窗口宽度和输入方式适配。首批 ABI 是 Android arm64、Windows x64、macOS arm64。

**取舍**：有一致的 UI 和可复用逻辑，仍需分别维护原生媒体、生命周期、文件权限及发行链路。Web、iOS 和 Linux 的支持不从 Flutter 的平台列表自动推导为本项目承诺。

**重评条件**：三端中的关键原生插件无法满足核心观看闭环。先尝试隔离的平台实现，再讨论整体框架变化。

## D2：Dart 实现协议与业务，Rust 暂不引入

**决定**：MVP 使用纯 Dart API 包、主应用 Repository 和 isolate；不引入 .NET 桥接，也不一开始把全部网络/数据库迁到 Rust。

**原因**：参考内核是 C#，无法直接复用为 Rust 库；早期难点是协议正确性和播放适配，Rust 不会自动改善原生解码或 Flutter 绘制。避免在协议仍频繁变化时同时维护 Dart DTO、Rust DTO 和桥接。

**未来边界**：若 CPU profile 显示解析/过滤/去重成为瓶颈，或出现第二个客户端要共享核心，可用 FRB 引入 `rust/bili_core` 和 Dart facade。先迁移无 UI 的纯计算；网络/下载若迁移则整块迁移，由 Rust 成为唯一所有者，禁止两套 CookieStore/下载状态机。

FRB 支持跨平台是可行性依据，但平台构建、取消、错误和流仍要验证。[FRB 平台说明](https://cjycode.com/flutter_rust_bridge/guides/cross-platform/overview)

**接入约束**：批量 API，显式句柄与释放、取消 ID、背压、错误映射、schema 版本；不逐帧/逐条弹幕 FFI，不跨边界传 native 解码帧。使用相同 fixture 测正确性与端到端收益，收益不足则保留 Dart。

## D3：一个播放器端口，media_kit 为待验首选

**决定**：主应用依赖 PlayerEngine/VideoSurface，由 bili_player 隔离后端；默认验证 media_kit。fvp 作为相同测试矩阵下的备选，不同时维护多套 UI 控制逻辑。

**原因**：媒体播放、独立音轨、headers 和桌面覆盖适合项目需求；Flutter 官方 `video_player` 文档仍列出 Windows/Linux 限制，不能只靠它构成三端方案。[官方播放说明](https://docs.flutter.dev/cookbook/plugins/play-video)

**定稿条件**：M0 通过三端 DASH pair/header/seek/sync、纳入支持范围的直播协议、资源释放和发行构建；明确系统下限及二进制来源。未通过的直播协议明确缩小 M3 范围。未通过前不得把“选用”写成“全部兼容”。

## D4：Riverpod + 按功能分层，保留少量独立包

**决定**：根应用按 feature 的 domain/data/application/presentation 组织；API、播放、弹幕三个包独立。Riverpod 提供状态和 DI，go_router 处理路由。

**取舍**：隔离高风险模块并保留可替换性，不为每个简单读请求生成用例类，不为每个页面拆 package，不叠加第二套全局状态/注入框架。

**重评条件**：出现独立发布/多应用复用需求，或单包边界持续发生可证实的依赖冲突，再拆包。

## D5：Web API 优先，各协议显式声明身份

**决定**：Web Cookie/WBI/CSRF 完成 MVP；HTTP Protobuf 用于点播弹幕；gRPC 和 App/TV 凭据按需要另加 profile。

**取舍**：可能先少一些只有 App 能力的功能，换取更清晰的登录和鉴权边界。不把失败后的随机换端点当作稳定性方案，不重放结果未知的账户写操作。

**重评条件**：目标功能无可用 Web 通道，并且独立 App/gRPC 登录、metadata、schema 和维护成本已验证。

## D6：弹幕由播放器时间驱动，渲染与网络分离

**决定**：点播使用确认的媒体时间 + 单调时钟插值；直播使用收到消息的单调时间。Flutter Canvas 局部绘制，输入与缓存均有界。

**取舍**：需实现轨道碰撞和布局缓存，但行为可测试，避免依赖某个弹幕包的隐含计时器。MVP 不实现高级脚本弹幕。

**重评条件**：同样输入和同步测试下，现成库或其他渲染器能持续降低 CPU/内存且满足许可与三端要求，可替换 painter；公共事件/时钟不变。

## D7：本地存储分责，单会话拥有播放资源

**决定**：SQLite 保存结构化数据，安全存储保存凭据，文件目录保存缓存/下载；MVP 只有一个活动播放会话。账号 epoch 与播放 generation 拦截旧异步结果。

**取舍**：需要凭据版本切换和下载一致性恢复设计；避免 UI 页面成为资源所有者。多账号 UI 与多窗口延后，但数据键从开始就带 scope。

**重评条件**：明确需要同时播放、多窗口或多进程下载，再设计新的所有权与进程间协议，不临时增加第二个全局播放器。

## D8：先交付 Windows 游客 UGC 预览，保留三端验收门槛

**决定（2026-10-05）**：响应首版可运行客户端要求，初始化三个平台入口，优先在当前 Windows 主机打通热门、搜索、详情、分 P、DASH、普通弹幕、本地历史与设置；同时实现 Web QR 与安全存储契约。默认选 H.264/AAC，并只展示服务端实际返回的可用清晰度。未实现的直播、下载、PGC 和云资产入口暂不显示。

**证据与限制**：Windows 受控服务验收了音视频两路 headers、302、Range/206、暂停、seek、倍速、surface 重建、释放重开；真实游客 UGC 解码到视频尺寸和音频声道/采样率。曾发现 `open()` 完成早于 native `on_load` 设置 headers 的竞态，已改为等待视频轨就绪再附加外部音轨，并验证音频参数。详细结果见 [M0 记录](validation/m0-results.md)。这不是三端 M0 或完整 M2 通过；完整扫码、30 分钟稳定性与性能预算仍待验。

**边界**：一个进程级 PlaybackSession 管理 PlayerEngine，路由与全屏转交 surface。媒体头拒绝 Cookie/Authorization；协议层的账号凭据不交给 native 后端。网络异常只有限次采用服务器备用 URL，不尝试绕过权限。

## D9：首版持久化与有界解码使用最小实现

**决定（2026-10-05）**：Drift schema 1 使用显式 SQL 创建设置与播放进度表，暂不引入代码生成。凭据在系统安全存储中使用两个槽和 active 标记切换；不写 SQLite 或普通文件。后续 schema 改动必须升版本并增加迁移测试。

**验证与约束**：SQLite 创建、重开、账号隔离、回退 seek 的进度覆盖有测试；Windows 安全存储以隔离 key 实测两次写入、读取和删除。弹幕大于 32 KiB 的二进制放入 isolate，最多两个活动、四个等待解码任务，每段最多 2 MiB/6,000 条；取消、epoch 和 deadline 在任务边界检查。应用最多保留当前相邻三段，绘制层另限制活动数和文本布局缓存。

## D10：UWP 风格工作区与独立页面标签

**决定（2026-10-05）**：按用户提供的截图、本机运行的哔哩哔哩 UWP 及参考仓库导航结构，自行实现顶部多标签工作区、横向频道导航、白底紧凑卡片与粉色指示条，替代初版侧栏。首页固定，浏览、搜索、视频、历史与设置支持独立页面标签。Windows 使用现有 window_manager 的隐藏标题栏和窗口控件；其他平台保留原生窗口装饰。

**状态边界（本轮修正）**：页面标签拥有各自的首页/搜索/视频状态；关闭标签释放页面请求，认证变化清理各标签旧状态。未关闭的视频页持续挂载，隐藏时移除媒体 surface 和快捷键响应，切到普通标签继续播放；进程级 PlaybackSession 按 owner 保存播放快照并复用唯一 native engine。普通标签往返沿用原播放源与当前进度，视频之间切换后恢复各自快照和播放意图。关闭当前播放标签停止播放，关闭其他标签不影响当前播放。移动系统后台仍由当前播放 owner 暂停。原先“切走卸载并依赖磁盘续播”的策略和“隐藏即暂停”的策略均已替换，验证见 [用户页、倍速与标签播放](validation/profile-playback-rates.md)。标签只在本次运行内保留，不承诺重启恢复或多窗口播放。

**能力边界**：首页补齐推荐、热门、动态、视频动态、番剧、国创、直播、放映厅、分区、排行榜、稍后再看和我的收藏入口。公开内容按各自端点加载，未接入的功能呈现明确状态与可用导航，不把热门列表当作其他频道数据，也不将入口完整等同于 M3/M4 已实现。此决定调整 D8 的入口隐藏策略；平台与协议验证仍按实际结果记录，见 [界面与多标签验证](validation/uwp-workspace.md)。

**播放器与列表扩展（2026-10-05）**：按本机 UWP 播放页调整为贴边黑色媒体区和右侧详情/选集/评论/推荐子标签；媒体区在子标签及响应式布局切换时保持同一面板。首页接入各频道只读数据，PGC/直播的浏览卡片通过系统浏览器打开官方 HTTPS 内容页，当前不扩充原生播放协议。私有列表的真实账号验证、内置 PGC/直播播放仍独立列为未验/未实现项。端点与结果见 [本轮验证](validation/player-workspace.md)。


## D11：共享观看设置与单次账户写入

**决定（2026-10-05）**：设置页与播放器配置弹窗消费同一类型化 SettingsController，沿用 SQLite settings 表，preferences.v1 JSON 内升级 schemaVersion=2，旧字段原值保留。视频动态独立横卡、直播独立房间卡和父子分区；账号/UP 头像使用公开图片 URL，不向图片服务器传账号 Cookie。

**账户操作**：新增 Web Cookie/CSRF 的点赞、投币、收藏、稍后再看与弹幕发送。只在用户明确点击后发送 POST；投币先选数量、收藏先选文件夹。写入仅尝试一次，网络/超时/响应格式等未知结果锁定对应操作；可核对的点赞/投币/收藏通过只读刷新解除未知态，不可核对的发送不在后台重放。会话 epoch 与 controller generation 隔离退出/换账号的晚响应。

**第三方空降**：默认关闭，启用后独立无凭据 transport 查询 bsbsb.top 片段；校验 CID、类别、动作、时间和媒体时长，仅消费 skip，不上报、不提交。手动提示/自动跳过复用当前播放会话，切源、暂停和关闭隔离旧事件。没有数据或第三方失败不影响视频。

**验证边界**：端点 fixture 与 fake 测试不等于真实账号线上验收；直播间仍打开官方网页，原生直播、下载、后台/PiP 不在本次接入。完整记录见 [界面控件与设置](validation/ui-controls.md)。

## D12：官方桌面式播放信息区与评论交互

**决定（2026-10-05）**：依据用户截图和本机官方“哔哩哔哩”桌面客户端实际界面，播放信息区改为简介／评论两个子标签，替代 D10 的四标签方案。视频操作放进简介，图标以悬停提示和语义标签解释；稍后再看与重新加载通过三点菜单访问。合集、视频分 P 和推荐分别支持展开／收起，合集条目中的分 P 保持独立展开状态。

**评论边界**：按用户本轮需求提前接入评论点赞、发送与楼中楼。协议仍为 Web Cookie/CSRF；页面通过应用控制器与纯 Dart 领域模型交互。读请求取消和分页／排序代次、账号 scope/epoch 阻止旧响应覆盖新状态；写请求只执行一次，未知结果不能自动重放。图片通过既有 NetworkAvatar 加载，不传账号凭据。

**验证边界**：只参考官方界面的信息层次和相邻 UWP 的协议入口，不复制资源或实现。真实账号点赞／发送不作为自动回归步骤。完整结果与未测项见 [播放页与评论交互](validation/video-comments.md)。

## D13：UWP 快捷键与按需富评论资源

**决定（2026-10-05）**：依据本机 UWP 4.8.18.0 和相邻源码，为已实现的观看/工作区能力建立纯 Dart 快捷键配置，设置支持编辑、开关和恢复默认；播放器单击只控制底部栏显隐。输入、弹窗、隐藏页面与临时倍速各自遵循焦点、可见性及播放源代次，工作区恢复不保存临时倍速。未实现的截图、PiP、下载等不伪装为可用快捷键。

**评论与资源**：评论身份标识、图片和表情来自现有 Web 评论字段，表情面板单独按需 GET，域模型与 UI 分离。发送表情仅插入 token 并沿用显式单次发送；不增加图片上传。按用户要求选取 UWP 图标字体、徽章和启动图标，来源清单与许可未明确的边界见 [资源说明](../assets/README.md)。这更新了前序阶段完全不复制视觉资源的采用范围，不增加相邻仓库运行时依赖。

**验证边界**：检查、原生回归、平台构建及在线只读结果见 [快捷键与富评论](validation/shortcuts-rich-comments.md)。账号评论发送不作为自动验证操作。

## D14：统一用户空间与有界只读列表

**决定（2026-10-05）**：个人主页与 UP 主主页使用同一 `profile` feature 和 `/user/:mid` 路由；账号、视频、评论、动态入口携带字符串 `UserId`，不按用户名推断身份。每个空间沿用独立工作区标签，资料和内容列表分别处理加载/失败，分类、筛选和分页保留独立状态并有容量上限。账号变化、关闭标签和刷新以取消及代次隔离旧响应。

**协议与采用边界**：参考本机 UWP 4.8.18.0 的个人/UP 空间和相邻 `UserDetailAPI`，使用 Web 资料、WBI 投稿、空间动态、收藏夹、关注与粉丝读取；不引入 UWP 的 App token 假设，不复制其凭据、代码或新增资源。空间专栏、独立合集、私信和编辑功能仍不在本轮范围。

**验证边界**：游客、已有登录会话、平台构建与未测项分开记录在 [用户主页验证](validation/user-profile.md)。风控、隐私和登录限制明确展示；公开端点可调用不等于所有用户所有列表可取得。

### 主页展示与共享动态内容（2026-10-05）

投稿使用主页专用横向卡片，统一显示封面时长、标题、观看/弹幕计数与发布时间；根据可用宽度和文字缩放调整列数与高度。首页动态与空间动态使用同一纯 Dart `DynamicPost` 模型和共享 UI，API 包统一解析两个 Web 动态端点的富文本、图片、视频与有界转发引用，Repository 经共享 mapper 映射，不互相导入 feature 的 data/presentation。表情使用服务端节点中提供的图片和大小，失效时保留文字 token；互动计数保持只读。具体能力与未验项见 [主页卡片与富动态](validation/profile-dynamic-style.md)。

## D15：首页布局驱动分页与有界图片缓存

**决定（2026-10-05）**：首页频道及所有子标签统一使用右下角刷新/回顶部按钮，移除列表底部和重复的顶部刷新入口。共享滚动组件在首屏、内容/视口变化、恢复可见和向下接近底部时检查分页；自动加载只作用于活动工作区中的当前频道/子标签。页面保持各自的滚动与查询状态，错误页等待显式重试。

**分页边界**：稳定 ID 去重；Feed 连续两页、Home 连续三页无新增内容时暂停自动请求并保留手动继续入口，图文动态允许跳过筛选产生的空页。动态的空/重复/循环游标暂停且不推进请求进度；动态/视频动态保留 200 条上限。取消、查询代次和账号 scope 拦截旧响应，不修改端点协议。

**图片与持久化**：app 组合根拥有图片缓存生命周期，core 不依赖 settings feature；共享图片组件仅接收公开图片 URL，不接收账号凭据。设置默认开启“缓存图片”，使用独立有界解码缓存及带 TTL/LRU 的账号隔离文件缓存；关闭后新图片不读写磁盘或留存解码缓存，已显示图片保持当前流。退出/换账号取消旧图片请求并清理旧私有缓存。采用已有 path_provider/path 与既有锁定的 crypto，不新增原生二进制。

**验证与采用范围**：按钮参考用户截图，UWP 仅借鉴刷新、状态保留和图片缓存职责，本轮不新增资源复制。离线行为、游客只读图片烟测、Windows 构建和未测平台分开记录，见 [首页刷新、自动分页与图片缓存](validation/feed-scroll-image-cache.md)。

## D16：三类内容页面共用原生播放会话

**决定（2026-10-05）**：按用户要求提前接入 PGC 和直播内置观看，更新 D11 等前序记录中的外部打开边界。保留视频页，番剧/国创/放映厅共用影视页，直播采用房间页；app 的唯一 `PlaybackSession` 通过类型化 `ContentPlaybackTarget` 解析 episode/room ID，复用 `bili_player` 已有 DASH/manifest/progressive 契约，不创建第二路 engine。

**状态与权限**：普通标签与播放所有权分开；选集、清晰度、重试隔离旧响应并保留用户播放意图。直播关闭点播 seek、倍速和续播。PGC 会员集可选，最终权限由 Web playurl 判定。SQLite 从 v1 升至 v2，只增加可空 episode 标识，保留旧数据，使影视历史回到正确页面。

## D30：点播弹幕滚动速度独立于播放倍速

**决定（2026-10-06）**：按用户要求，普通视频和影视弹幕继续按确认播放位置加载分段并触发显示，滚动与固定弹幕停留改用不乘播放倍速的单调动画时间。独立弹幕速度配置继续有效；调整播放倍速不清空或改变已显示弹幕的滚动进度。

**边界**：两个时钟共同响应暂停、缓冲、seek 和过期位置样本。seek 用当前倍速换算历史年龄并重建；应用时间窗覆盖对应媒体历史及仍可见的项，已调度 ID 随有界窗口淘汰，回退 seek 清理去重以允许重播。沿用单 Ticker／局部 Canvas，不新增网络、依赖或持久化设置，直播仍使用独立到达时间。验证见 [弹幕速度与播放倍速](validation/danmaku-playback-rate.md)。

## D31：CDN 默认自动调度，只优先服务端返回的线路

**决定（2026-10-06）**：按用户要求增加播放设置中的 CDN 选项。默认自动保留 B 站播放接口返回的顺序，由系统／代理解析域名；常规 CDN 与腾讯／华为／阿里／百度偏好只调整本次响应中已有地址的优先顺序。音视频分别处理，缺少对应线路保留其他地址，不重写签名 host/path/query 或 IP，不引入测速、自定义 DNS 或新依赖。普通视频、影视和悬停共用排序，直播协议独立；下次解析媒体源生效。偏好快照 13 → 14，旧值缺失／非法时自动补缺，数据库 schema 不变。

**悬停恢复**：临时预览打开每次预算 8 秒，最多使用一次服务端备用地址，释放完成后才创建下一引擎；取消和 generation 阻止过期重试。恢复前台／工作区时按当前悬停重启。stop 失败不等于 dispose 失败，只有未确认释放时禁止后续新预览。真实样本修复前可播，受控 403 仅证明恢复路径；验证及未测项见 [CDN 与悬停恢复](validation/video-cdn.md)。
