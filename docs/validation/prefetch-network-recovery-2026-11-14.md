# 点播预读断流恢复

日期：2026-11-14（Asia/Shanghai）。

## 问题与参考

播放位置小于缓存终点时，原生 HTTP 续读可能已经失败，但缓存中的音视频仍能播放。现有 `NativeErrorMonitor` 将位置继续推进视为运行恢复，因此可能直到缓存耗尽才重新加载。

只读对比 PiliPlus `cab0114a21ce7fad5b90b9a4d788d35d313d25f9`：`lib/plugin/pl_player/controller.dart:1101` 订阅原生缓存、`:1122` 处理错误、`:962` 的 `refreshPlayer` 从当前位置重开；其点播重试经节流和延迟后仍要求 `isBuffering && buffered == 0`。`lib/utils/storage_pref.dart:857` 配置原生缓存窗口和字节上限，没有独立预读恢复探针。实际 overrides 和锁文件、许可边界见[参考记录](../references.md)。仅参考职责与行为，没有复制参考应用源码。

## 实现与边界

- 原生 mpv 仍拥有媒体读取、缓存和自身 HTTP 重连；不重建 HTTP 代理、字节缓存、MP4 索引或逐帧原生查询。
- [NativeBufferRecovery](../../packages/bili_player/lib/src/native_buffer_recovery.dart) 在 HTTP／连接／超时／读取中断错误或提前输入 EOF 后启动；另通过既有 SDK 路由观察 `demuxer-cache-state` 的 idle／eof 字段，原生正在读取却 5 秒没有新增缓存时也启动检查，覆盖没有及时报错的挂起读取。只要缓存终点重新增长，就取消这次检查；位置推进不能替代网络读取恢复证据。原生因缓存满而 idle、片尾和正常增长不会启动探测；不新增周期原生属性查询。原生读流挂起时可能延迟 cache-time 通知，仍在播放的状态不强制等待该通知到达。
- 错误后每隔 5 秒探测实际媒体源，使用当前源允许的请求头和 `Range: bytes=0-0`；DASH 音视频均须可达。每次探测总超时 3 秒，最多 24 次并受 2 分钟总截止限制，重复日志不能延长预算。无 Cookie、无账号 API 调用、不跟随探测重定向，不落盘媒体地址／请求头，也不记录原始异常。
- 离线或临时服务错误时保留当前播放，继续消耗已有缓存，不因为探测失败清空缓存或暂停。源地址过期、媒体缺失和重定向也可交给既有解析／原生加载流程处理；探测不声称媒体可完整播放。
- 确认线路可达但原生缓存仍未增长后，发送当前源失败证据，沿用 `PlaybackSession` 已有的 URL 刷新／备用 CDN、当前位置、最后画面与有限重开预算。不会新增另一组播放器或第二路音频；失败重开仍可能有短暂重新加载，不能宣称保留全部原生包缓存或绝对无缝。
- 暂停、seek、换源、释放和旧源回调取消探测；过期探测结果不能恢复新源或覆盖用户暂停意图。仅覆盖 HTTP(S) 正常点播／听视频，不用于直播、静音悬停预览或离线文件。
- 应用原有整组恢复次数与截止时间不变；不新增设置、数据库 migration、依赖或锁文件修改。

## 验证

使用 Flutter 3.47.6／Dart 3.13.5 和当前锁定 media-kit `302d60eedc55ca677e911e529569b1e14d8c2e7e`，未修改依赖、锁文件、相邻仓库或 Pub 缓存。

- `tool/check.ps1 -SkipPub` 全阶段通过：根应用 5356 通过、13 跳过；API 920、播放器 256、弹幕 161、mux 5 通过。播放器 3 项显式原生用例未配置环境而跳过；未设置 `BILI_MUX_LIBRARY`，mux 10 项原生用例跳过，不计为原生通过。最终根静态分析再次通过。
- 定向缓存恢复、原生状态解析、错误观察和脱敏测试 48 项通过，包含缓存未通知、输入提前 EOF、静默读取停滞、缓存满 idle、位置推进、缓存增长、重复错误截止时间、单飞、取消和真实本机 HTTP Range／重定向／过期地址探测。
- [Windows 新增回归](../../integration_test/windows_prefetch_recovery_test.dart) 对真实 DASH 分轨分别关闭供数连接、保持连接却停止供数。断网 16 秒内保持原 generation、位置继续推进、没有进入网络缓冲或因离线探测清空缓存；恢复供数后，两轨小范围探测均成功，沿用正式 `PlaybackSession` 自动恢复，缓存继续增长。两种场景触发恢复时分别仍有 110.080／110.208 秒缓存，恢复后缓冲终点分别到 140.750／140.625 秒，双轨均有真实解码证据。两项均通过，并已加入 `tool/test-windows-buffer.ps1`。
- 通过 DTD 对独立受控入口完成热重载，无运行时错误；两种场景在该入口再次通过，关闭前已等待会话和原生播放器释放。
- 文档 689 个相对链接、缓冲脚本 PowerShell 解析和 `git diff --check` 通过。

首轮 HTTP 探测测试被 Flutter 的默认 HTTP mock 返回 400 阻断，随后明确在测试内使用真实本机 HTTP overrides，定向套件通过。首轮原生夹具供数范围不足以产生所需缓存证据，调整为仍未读完的长 DASH；后续原生失败进一步确认 `/idle` 子属性不受当前 SDK 支持，且最后一批缓存增长可清除较早的 HTTP 错误，因此改为监听完整缓存状态，保留提前 EOF 证据后，两类故障均通过。没有把这些失败计为通过。

扩展的旧窗口回归在初始／暂停／推进／400 秒 seek 均确认约 120 秒原生前向缓存，最后切换到 60 秒静音短片的缓存断言失败。将本轮修改的三个生产文件还原为 `HEAD ab1df684` 的内容，在忽略目录内构成隔离播放器包并临时路由解析，同一短片断言仍在 `windows_buffer_ahead_test.dart:179` 失败，确认是已有问题，没有为通过该扩展用例修改原断言。

同一原始 HEAD 的播放器对新增断流用例也失败：断网恢复后播放位置从约 16 秒继续到 31 秒，缓存终点仍停在 130.538 秒，探测和恢复均为零，复现用户描述的缺口。本轮代码的两类故障用例均通过，形成原始代码失败／修复代码通过的真实原生对照。隔离验证使用 `try/finally` 恢复原始 package 配置字节，未改动工作区生产代码、锁文件或缓存；基线材料在 `build/validation/prefetch-baseline/`，结果在 `prefetch-window-head.log`／`prefetch-recovery-head.log`。

本轮 Windows 为 Debug 功能和真实原生恢复验证，不是性能或 Release/AOT 验收。受控 HTTP 不替代真实 CDN、人工听音画同步、长期弱网；Android、macOS、iOS、Linux 未做本轮构建／设备测试。原生优先续读不改动已有缓存，回退重开存在短暂重新加载的可能，不宣称恢复过程无停顿。
