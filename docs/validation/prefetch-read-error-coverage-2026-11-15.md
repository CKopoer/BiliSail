# 点播提前截断错误与恢复入口覆盖

日期：2026-11-15（Asia/Shanghai）。

## 现场与原因

用户报告本地 `build/windows/x64/runner/Release/bilisail.exe` 的缓冲终点停止增长，播放逐渐追上后才重加载。核对实际进程 4560、启动时间 15:48:41，保留该进程的脱敏播放日志及产物摘要。`data/app.so` 的 SHA-256 为 `CFB380C1650B55A5B36BC5B81DBF214CBD1DD1F07D3AA62DBD63C68BCDC2BA42`，未混用安装版或其他进程的日志。

正式 DASH 实例 playerId=24 为 H.264／AAC、2 倍速，总时长 1490.472 秒：

| 北京时间 | 证据 |
| --- | --- |
| 16:02:52.465 | `ffmpeg/demuxer` 报 `corruptPacket` warning 和 `prematureRead` error，后者主类别为 `unknown`；位置 814.040 秒，缓存终点 934.056 秒，领先 120.016 秒 |
| 16:03:52.466 | 位置推进到 934.040 秒，缓存终点 934.270 秒，领先仅 0.230 秒；音频解码错误触发 `playbackStalled: audioDecodeError` |
| 16:03:52.705–53.176 | 从同一位置重开，playerId=25 成功确认两轨，后续缓存恢复增长 |

错误间隔约 60 秒、媒体位置推进 120 秒，与 2 倍速消耗原有缓存吻合。首次提前读断没有进入预读恢复，最终由音频解码错误触发重开。

[NativeErrorSummary.classify](../../packages/bili_player/lib/src/player_diagnostics.dart) 已把 `partial file` 识别为 `prematureRead`，却遗漏其 I/O 主类别；[MediaKitBackend](../../packages/bili_player/lib/src/media_kit_backend.dart) 原来仅按四个主类别启动提前恢复，因此漏接。现场没有保存原始文本，不能逐字还原消息；根据分类分支及隔离复现，确认此类错误存在缺口。

现场只有事件触发的原生快照，没有连续 idle／EOF／探测结果，不能精确还原静默探测没有兜住的具体取消点。idle 或正常输入 EOF 取消静默探测，仍是避免正常满缓存、片尾误重开的必要保护，本次不改变该规则。

## 修复及其他错误审查

- `partial file`、明确的分片打开失败和清单重新读取失败统一归为 I/O。读断／分片详情优先于泛化的时间戳匹配，避免消息中 `pts` 等内容遮蔽真正错误。
- 两个 SDK 日志入口统一交给 [NativeBufferRecovery.reportError](../../packages/bili_player/lib/src/native_buffer_recovery.dart)，避免分别维护容易漂移的类别列表；使用穷尽的 enum switch，新增主类别必须明确选择是否属于读取失败。
- 另发现 **TLS 已分类却未接入此恢复路径**，本次一并接入；原来的 `segmentRead` 可能落入泛化的 `openFailed`，本次也补齐。
- 保持当前位置、倍速、音量、最后画面、暂停意图及账号／源代次隔离。明确读错立即交回现有会话恢复，最多三次打开及同一 deadline；不新增重试层、设置、依赖或网络缓存。

| 错误／状态 | 处理边界 |
| --- | --- |
| HTTP、超时、连接、TLS、明确 I/O／提前截断／分片读取失败 | HTTP(S) 正式点播的同一有界提前恢复路径；不等缓存耗尽，也不要求原生仍在 reading |
| 音频解码错误 | 保留现有音频错误监测及整对恢复 |
| 明确硬解／视频输出失败 | 保留现有视频错误监测及整对恢复 |
| 普通坏帧、参考帧缺失等 | 保留进度／解码健康判断，不把每次 warning 都变成重开 |
| 满缓存 idle、正常输入 EOF | 取消静默探测；没有明确错误时继续消费缓存 |
| 普通文件不存在、泛化打开失败、未知诊断 | 不凭无上下文文本归为网络读错；沿用打开就绪、真实 END_FILE、提前播放结束和播放健康检测的现有出口 |
| 暂停、seek、旧源、销毁、直播、离线文件、静音预览 | 保留既有资格、取消和范围限制；点播预读入口不代替这些路径的独立策略 |

这次补齐了已确认的分类／路由遗漏，不代表原生将来的所有错误文案都能识别。未知文本、缺少错误信号及单轨状态聚合仍可能形成覆盖边界；不能用“所有 error 一律重开”保证恢复。

## 回归与验证

- 分类回归覆盖容器／root atom 提前截断、分片和清单读取失败、URL query 脱敏。新增行为断言在原实现下失败：预期 `inputOutput`，实际 `unknown`。首次测试自身缺少必填 phase 导致编译失败，修正测试后才记录有效行为失败。
- 缓存恢复回归覆盖可播缓存、原生已 idle／EOF、重复错误去重及 HTTP／超时／连接／TLS／I/O。坏包、时间戳、硬解建议、缺失属性、无上下文文件／设备打开错误和未知文本不误触发预读恢复。
- [Windows 预读回归](../../integration_test/windows_prefetch_recovery_test.dart) 在真实本机 HTTP DASH 双轨已经解码、播放推进且缓存充足时，分别通过 SDK log 流注入现场等效的提前 `partial file` error，以及通过 SDK error 流注入 TLS 失败。验证分类、两个原生入口、失败去重、正式 `PlaybackSession` 完成有界重开、进度继续推进和两轨恢复；原始合成 URL／query 不得进入诊断。
- 最初尝试以实际截断 HTTP 音轨控制错误时序：SDK 缓存通知可能在阻塞读取期间延迟；即使原生缓存查询确认已有约 56 秒可播数据，某些运行仍未在 15 秒内提前报出读错。也遇到保留画面的 opening 状态提前满足位置／缓冲断言，以及一次多文件 Windows 测试启动调试连接失败。这些失败没有计为通过。最终通过原生 SDK 的既有事件流固定现场的提前错误信号，不把稳定触发这条信号与复现原始媒体／CDN 故障混同。

- `tool/check.ps1 -SkipPub` 最终全阶段通过：打包边界、格式、静态分析及 **7,144 项离线测试**，其中根应用 5,628、API 997、播放器 353、弹幕 161、mux 5。根应用 13 项符号链接权限用例、播放器 3 项可选原生用例跳过；未配置 `BILI_MUX_LIBRARY`，mux 10 项原生用例跳过，均不计为原生通过。最终集成用例整理后，根静态分析与任务文件格式再次通过。
- Windows 原生预读分组 **4 项通过**：明确断网共享三次打开额度、静默挂起可达后探测恢复，以及本次两条 SDK 错误入口。提前截断错误／TLS 故障发起恢复时分别仍有 **120.201／120.125 秒缓存**；重开后位置分别推进至 10.666／10.416 秒，缓存终点 130.773／130.560 秒，两轨确认成功、无音频解码失败。静默探测恢复时仍有 110.208 秒缓存。日志为 `native-prefetch-pass.log`。
- Windows 正常 DASH EOF 分组 **4 项通过**，覆盖完整等长／不等长 HTTP、完整不等长本地文件，以及现场等效 140.5 秒视频／139.853 秒缓存终点的长片。长片越过原失败位置至 25.066 秒，随后尾部 seek／正常结束通过，失败数为零。日志为 `native-eof-final.log`。
- 独立无账号双轨调试入口完成 Windows Debug 构建及运行；DTD 热重载成功，运行时错误为空。退出前等待 engine 释放、关闭本机 HTTP 控制端口；没有操作用户播放会话。首次热重载传入 HTTP 形式 VM 地址未匹配 DTD 注册项，改用已注册的 WebSocket 地址后成功。
- 六个生产／回归文件的最终摘要与验证时一致，记录在 `final-source-manifest.json`；本次文档相对链接、任务文件格式及 `git diff --check` 通过。

本轮原生运行是 Windows Debug 功能验证，不是 Release/AOT、人工音画或性能验收。未执行 Android、Apple、Linux 构建／设备测试；没有改动原生 SDK、媒体 fork、依赖或锁文件。用户原先的进程 4560 与 Release 产物保持原状，修复需要重新构建后生效。

## 归因限制

已确认应用漏接提前读断，造成恢复延迟。原始输入为何截断，现场缺少逐轨 HTTP、原始字节和媒体包证据，不能断定是 CDN、网络、封装还是其他原因。受控合成媒体与 SDK 注入验证应用边界，不代替原始 CDN、人工听音画同步、长期弱网或其他平台设备验收。
