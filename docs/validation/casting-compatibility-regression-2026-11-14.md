# 云视听小电视投屏加载失败修复

日期：2026-11-14。修复基于同步后的 `origin/master` `dbbf5f4d`，保留其中的评论图片、鼠标手势和播放倍速修复。

本记录只覆盖默认路径的回归缓解，未修复当时主动开启弹幕后的加载失败。随后针对用户确认的云视听 **1.8.9** 核对官方接收逻辑，补齐身份取流、初始弹幕与时间单位字段，见[弹幕模式后续修复](casting-danmaku-receiver-1.8.9-2026-11-14.md)。

## 现象与原因

用户反馈：上次投屏扩展后，云视听小电视显示“加载失败（错误码：null）”；此前版本可以播放同类视频，但没有电视弹幕。

确认的代码回归是交接路径自动变化：

1. `CastingController.connect` 将设备描述存在 `NirvanaControl` 等同于接收端可自行解析完整内容，自动传入 `receiverResolves=true`。
2. `ApiCastMediaRepository` 因此跳过原来的视频／番剧 TV `durl` 获取，直播也不再提供已解析的媒体地址。
3. `DlnaCastRepository.setMedia` 又仅根据设备服务声明，将 `CurrentURI` 强制替换为 `bilibili://projection`。
4. 电视可能接受 SOAP 控制请求，但后续仍无法加载该身份请求。SOAP 应答与扩展元数据可解码，都不能证明电视的专有取流会话、账号与版本已经兼容。

此前测试只确认扩展报文的结构、解码和控制应答，缺少“声明 B站服务但仍需要完整媒体直链”的接收器回归。不能从错误码 `null` 推断云视听内部具体是哪一个字段或鉴权校验失败，本次没有将其归因于一个未经抓包确认的字段。

## 修复行为

- 所有设备默认继续使用兼容播放：视频／影视获取 TV 完整音视频地址，直播保留 AVC HLS／FLV 地址选择；不因发现服务自动跳过取流，不向默认交接附加身份元数据或弹幕开关命令。
- `CastMedia.receiverResolves` 默认 `false`，由显式解析请求一路携带至设备适配器。适配器不再自行根据设备服务推断模式，防止应用层请求了直链却在 data 层又被覆盖。
- 仅对声明同主机 B站服务的设备提供“电视弹幕（实验）”，每次面板打开默认关闭。主动开启后保留原实验路线，不宣称已完成云视听实机兼容。
- 开关改变本身不发送请求；当前设备模式变化后，用户点击“按当前设置重新投屏”或重新选择设备，才执行串行 Stop／重新解析／设置／Play。同设备、同模式的重复选择仍去重，进行中的操作不能被切换模式改变。
- 实验模式加载失败后可关闭开关并显式重投，或者重开面板使用默认兼容模式；没有新增自动播放写命令重试，没有传送账号凭据，也未改变直播入口、离线／iOS 能力边界或全局设置存储。
