# Windows Release 正常预读 EOF 误判修复

日期：2026-11-14（Asia/Shanghai）。

## 现场与定位

用户报告刚生成的 `build/windows/x64/runner/Release/bilisail.exe` 播放视频时提示“音视频播放失败”。窗口枚举确认实际执行路径为此本地 Release，进程为 33388。其 EXE／`data/app.so` 的 SHA-256 与 19:20 的构建清单一致，分别为 `5CC2F6A0A2E4E41CC510391619445C7EEFFE3F0F970E18C392944D9D8E5D5AC5`、`9A0E671D4DEA6EB6E1AFEC9FEFD36FC82E70161737A5D82BC64D0929558F1809`，没有将商店安装版的旧日志当作本次现场。

本地脱敏日志 `playback-1794656144553372-33388.log` 中，20:41:18–20:41:40，同一 140,500 ms 视频的六次打开（playerId 66–71）均成功解码 H.264／AAC 并创建视频输出；首次在播放位置 19,633 ms 失败，后续分别在 20,000、20,833、20,833、20,866、20,866 ms 失败。六次失败的缓存终点均为 **139,853 ms**，尚余约 119 秒媒体；没有对应 `playbackStalled`、缓存暂停或音视频解码错误。打开阶段的未分类 error 在成功对照中也存在，不能仅据它判断解码失败。

问题位于 [NativeBufferRecovery](../../packages/bili_player/lib/src/native_buffer_recovery.dart)：旧逻辑看到原生输入 `eof=true`，且 `duration - cache-end > 0.5s` 时，立即发出整对媒体失败。此次差值为 **0.647 秒**。这条启发式来自 `6fac13dd` 的明确预读错误立即恢复分支，和随后增加的 `NativeRebufferMonitor` 不是同一触发路径。

[mpv 属性说明](https://mpv.io/manual/stable/#properties-demuxer-cache-state)将 `eof` 定义为读取线程到达输入末尾，而 `cache-end` 是估计缓存时间戳。二者不提供“网络损坏”的证明；DASH 两轨的真实尾部可以不同，缓存终点也不必等于容器总时长。旧判断把正常预读结束当作断流，沿 `MediaKitBackend` → `SharedPlayerEngine._fail` → `PlaybackSession` 既有重试链暂停、重开并耗尽最多三次打开额度。

这解释了起初可播放约 10 秒、随后重开很快又失败：2 倍速先消费约 20 秒后，120 秒预读窗口才覆盖输入尾部；从约 20 秒续播则很快再次遇到相同尾部差值。失败由应用主动触发，与剩余缓存是否足够无关。

## 原始实现的独立复现

测试素材均为 FFmpeg 合成，不读取账号、媒体签名 URL 或凭据。原生对照直接加载此次 Release 目录内的 `libmpv-2.dll`：

| 场景 | 结果 |
| --- | --- |
| 8.7 秒视频 + 8.7 秒音轨，完整 HTTP 供数 | 原生和应用播放器均正常结束 |
| 8.7 秒视频 + 8.05 秒音轨，完整 HTTP 供数 | 原生正常结束；旧恢复监测器在约 0.167 秒请求恢复，旧应用播放器约 0.3 秒进入 failed |
| 同一对不等长文件，以本地路径打开 | 旧应用播放器正常结束，未安装 HTTP 预读恢复监测器 |
| 140.5 秒视频 + 139.86 秒／44.1kHz AAC，完整 HTTP 供数，2 倍速 | 旧应用播放器在 19,933 ms 失败，duration=140,500、buffered=139,853 ms，与现场数值和时序吻合 |

两轨 HTTP 均完整返回，没有注入网络错误。原生样本 `eof-cached=true`、`underrun=false`，H.264／AAC 解码和播放结束均正常。将同一原生事件序列送入旧监测器会请求恢复，修复后为零次恢复。

已证明正常输入尾部可以稳定触发本次缺陷；现场没有保存原始媒体包和逐轨 EOF 事件，不能进一步把原视频的 647 ms 差值精确归因于某一轨的编码／封装参数。

## 参考与简化

只读核对 PiliPlus `217fb54f51f6764176319bbdedab2a7522d75401` 的 `lib/plugin/pl_player/controller.dart`：`:960` 的 `refreshPlayer` 使用当前位置重开，`:1099` 附近订阅 SDK 缓存／缓冲，`:1118` 附近的点播重试由明确错误触发并检查缓冲状态，没有用总时长与估计缓存尾部差值推断断流。

实际 overrides／锁文件中，核心及库插件为 `My-Responsitories/media-kit` 的 `73771ec38176be2d984a3049c28177bce23b54a0`，视频为 `bggRGjQaUbCoE/media-kit` 的 `85f0a69ea66b100882b27a3375c72e5155375343`。仅借鉴原生播放与应用恢复的职责边界；独立实现，没有复制 GPLv3 应用代码、修改相邻仓库、媒体 fork、Pub 缓存或依赖版本。

- 删除输入 EOF 的 0.5 秒差值判错，也不把未知端点 EOF 转成线路探测。
- 输入 EOF 表示当前读线程不再读取，取消尚未完成的静默读探测、定时器和迟到结果；不干预仍能正常消费的缓存。
- 从原生观察器到恢复器移除不再需要的 `cacheEndSeconds` 参数。缓存条和诊断仍可展示原生估计值。
- 明确 HTTP／I/O／超时／音频解码错误保持既有有界恢复；仍在读取却没有新增缓存的静默挂起、反复原生缓存耗尽、真正提前播放结束也保留原有出口。没有扩大重试次数、引入第二组播放器或新增常驻轮询。
- 修正旧预读集成用例的断网分支：D89 后明确 HTTP 断开会立即有限重试，旧断言却仍要求离线 16 秒内不重开。现在验证三次失败后停止自动重试、网络恢复后显式重试能继续；静默挂起分支继续验证保留可播缓存并探测双轨来源。

## 验证材料与边界

单元回归覆盖现场两轨尾部差异、未知时长、输入 EOF 取消正在运行的探测、迟到结果、EOF 后明确网络错误仍只报告一次，以及真正提前播放结束仍暂停并报告 `videoInterrupted`。新增 [Windows DASH EOF 回归](../../integration_test/windows_dash_eof_test.dart)，由 [缓冲回归脚本](../../tool/test-windows-buffer.ps1)生成合成素材并运行，覆盖上述四种正常输入及现场等效长片；长片必须越过原失败位置，再从缓存跳转到尾部并正常结束。

现场摘录、原产物备份与摘要、直接原生对照、原始实现失败记录和修复日志位于忽略目录 `build/validation/release-playback-failure-2026-11-14/`。共享工作区同时存在网页登录及其他任务修改，最初全量检查在该处出现格式／编译错误；最终播放器修复的独立验证使用 `build/eof-fix-source`，基于已提交的 `56df571a` 加本次文件，不纳入同期未提交改动。

- 新增 EOF 行为用例在原始实现下有 5 项失败；修复后的缓存恢复／原生事件／共享引擎定向 100 项通过。
- 隔离工作树运行 `tool/check.ps1` 全阶段通过：根应用 5,494、API 935、播放器 318、弹幕 161、mux 5，共 6,913 项离线测试；根应用与各包格式和静态分析通过。根应用 13 项符号链接权限用例、播放器 3 项可选原生契约用例跳过；`BILI_MUX_LIBRARY` 未配置，mux 10 项原生用例跳过，均不计为原生通过。
- 新增 Windows DASH EOF 的四种场景首先在共享工作区通过：长片从 25,000 ms／139,853 ms 缓存位置继续，随后跳至尾部并正常结束，失败次数为零。原始等效长片在 19,933 ms 进入 failed，形成数值和时序对照。
- 隔离工作树的 Windows 原生预读断流／挂起 2 项、反复缓存耗尽恢复 1 项及 EOF 4 项全部通过。静默读挂起恢复时仍保留 110,166 ms 缓存，双轨探测后缓冲继续增长；反复缓存恢复位置为 3,708／7,708 ms，备用后推进到 11,791 ms；EOF 长片越过 25,066 ms 且零失败，尾部 seek 和正常结束通过。
- 独立普通 Flutter 运行入口用同一不等长双轨 HTTP 素材正常结束，确认音视频均解码；通过 DTD 热重载成功，运行时错误为空。退出入口先等待 engine 释放并关闭本机 HTTP 服务，没有操作用户账号。
- 同一入口使用 `flutter run --release` 完成 AOT 构建并实际运行，记录 `release=true`、`phase=ended`、位置 8,666 ms，音视频均已解码；完整 HTTP 的不等长双轨没有失败。结果在 `runtime-release-result.json`，退出前等待原生释放并关闭服务。
- 验证入口退出后，重新以普通 `lib/main.dart` 构建 Windows x64 Release，通过后完整复制到 `build/windows-eof-fix/Release/`，逐一核对全部 115 个文件摘要。`data/app.so` SHA-256 为 `244D5740A228BD2F540CA525AA5876A1AE227159E90CC9595F03CF4DB43D6D15`；mpv DLL 保持原始 `8FA6AF29A94623D7D1E16BC6DB48668F321E3FC9F1EAA86A8DF8D61EC57F00E3`。普通入口构建日志为 `release-main.log`，九个任务源码／测试／脚本与共享工作区一致，记录在 `fixed-release-manifest.json`；交付目录需整体保留。
- 新文档相对链接、缓冲脚本 PowerShell 解析及本任务 `git diff --check` 通过。

隔离冷构建曾受原生归档下载超时、NuGet 未配置、并行离线测试占用 SQLite DLL，以及中断生成后留下默认安装前缀影响。这些失败没有计为通过。最终顺序执行，复用与固定 SHA-256 匹配的既有 mpv／ANGLE 原始归档，使用 Microsoft Authenticode 校验有效的 NuGet 6.14.0，将安装前缀显式设为隔离工作树的 runner 目录后完成构建；没有修改依赖缓存或生产 CMake 来绕过校验。

Windows 以外平台未做本轮构建／设备验收；受控合成素材不替代原始 CDN、人工听音画同步和长期弱网验证。没有将 Debug 原生功能回归当作性能结论。
