# fvp 恢复播放后反复停帧与中断

> 历史记录：fvp／MDK 已于 2026-11-12 移除。下文保留当时实现与验证事实，相关源码、资产和专属命令已退役；当前行为见[移除记录](fvp-removal-2026-11-12.md)。

日期：2026-11-09（Asia/Shanghai）。针对本机 `build/windows/x64/runner/Release/` 普通入口的实际播放日志定位，在 `6c118bcd` 上修复。

## 证据与原因

本轮读取进程 30612 的本地脱敏播放日志，没有读取账号凭据或媒体 URL：

- 21:41:44，fvp、2 倍速、视频进度 193366ms，音频伴随管线报告提前结束，触发第一次有界恢复。
- 21:41:55，视频停在 207133ms，音频已到 210488ms，原生缓存端点为 327156ms；共享检测器在视频静止 1500ms 后暂停两轨并恢复。
- 21:42:03，再次出现同类情况：视频停在 211366ms，音频已到 214976ms，缓存端点为 327790ms。连续失败耗尽原有恢复预算，最终显示中断。

后两次有实际音频推进和充足缓存，不能归为普通缓冲不足。原生桥的首次时钟接入要求音频位置始终处于暂停目标的 ±100ms 内，但 `onSync` 是视频准备呈现时才调用。首次回调稍晚、尤其倍速播放或恢复后音频已越过该范围时，原代码永远返回旧目标，健康检测随后正确发现视频不再推进。受控 C++ 回归以首次读取时音频已前进 300ms 复现旧实现失败，再覆盖多个倍速与非零目标。

最初音频提前结束的具体原因没有完整网络／原生读取证据，无法仅凭结构化日志判断是 CDN 截断、原生读取还是媒体本身问题。本次修复的是已复现的恢复后视频时钟锁死，保留真实提前结束的检测与有限线路恢复。

## PiliPlus 对照与修改

只读核对相邻 PiliPlus `4fce4bb5a35c425aee759ef9263352316a29e355` 的 `lib/plugin/pl_player/controller.dart`：

- `_createVideoController` 通过单个 mpv 实例的 EDL 双流加载视频／音频，先暂停打开。
- `play`／`pause`／`seekTo` 直接调用原生命令，位置、缓存、buffering 来自原生事件；应用不另按一个固定的首次时钟窗口冻结视频。
- `pubspec.yaml` 的 overrides 与锁文件实际固定核心／库插件到 `My-Responsitories/media-kit` 的 `73771ec38176be2d984a3049c28177bce23b54a0`，视频实现为 `bggRGjQaUbCoE/media-kit` 的 `85f0a69ea66b100882b27a3375c72e5155375343`。该路径使用 mpv，不能把它的 EDL 命令直接移植到 MDK。

借鉴原生时钟负责同步、应用消费状态的职责划分，独立修复本项目的 [fvp 原生桥](../../packages/bili_player/src/fvp_audio_activity.cpp)：恢复时记录单调时间，首次接入允许音频在本次实际播放时间及原生倍速内正常推进；目标之前的旧时钟与不可能已到达的未来旧时钟仍被过滤。返回值始终是真实音频呈现位置，单调时间只验证首次位置是否可能属于本轮播放，不生成播放进度。接入后继续跟随原生时钟；暂停、seek 代次、停止和自然 EOS 保持原语义。重复 play 不重置接入起点。

没有扩大 2 秒单轨中断门槛、30 秒同步缓冲等待或应用恢复次数，没有增加新重试层、切换用户后端或修改个人媒体依赖。PiliPlus 应用为 GPLv3，本轮未复制其源码／资源或修改相邻仓库；SDK 与原生桥既有许可边界不变。
