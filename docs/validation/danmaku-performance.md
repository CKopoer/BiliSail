# 密集弹幕性能优化

日期：2026-10-10。基线提交 `2ed744c93fff6c0b42ed50f270e81e01a2d52028`；修复后为当前工作区。工具链 Flutter 3.47.6 / Dart 3.13.5。

## 定位

- 点播 `replaceEvents → _updateLaneHeight` 原来对最多 500 条待调度事件逐条创建完整 `TextPainter`。布局缓存只有 256 项，重复刷新同一窗口仍会循环淘汰；描边模式还会预先创建第二份段落。未来事件和最终被丢弃的事件也付出这笔开销。
- 直播 `frame` 原来先布局全部到期消息来确定行高，再执行过期、容量、合并和轨道丢弃。500 条突发消息在一帧中集中布局，前一遍还会挤出后一遍需要的缓存。
- 两种调度器的每个候选、每条轨道都扫描完整活动列表。
- 默认模糊阴影即使命中 `TextPainter` 缓存，仍在每帧重新进行模糊绘制。Windows Profile 的阴影 raster P95 为 55.77–66.67 ms；普通/描边仅 2.31–4.73 ms，因此只优化 Dart 调度无法解决默认样式的主要卡顿。

## 方案比较与来源

用户指定的 `dart_simple_live` 本地提交为 `ba828e6783b176ea5709fcd09f0eb01dfaceeb51`。其播放器使用 `canvas_danmaku ^0.2.7`，复用 `DanmakuScreen`，过滤后逐条添加。该依赖的 0.2.7 预创建/复用段落；多于十条时在每帧另录制 Picture 再绘制，普通文字采用描边而非本项目的模糊阴影。

本轮同时检查 pub.dev 当前 0.3.3（2026-08-27 发布）的源码：采用单 Ticker、文字 `ui.Image` 预渲染、按 DPR 绘图、静态项独立通知与显式释放，方向与实测的阴影热点相符。来源、归档校验和许可范围见 [参考记录](../references.md)。生产代码独立实现，没有引入运行时依赖。

| 方案 | 本轮判断 |
| --- | --- |
| 仅缓存 TextPainter/Paragraph | 可减少布局，无法消除模糊阴影每帧的 raster 开销 |
| 每帧录制批量 Picture | 仍包含需要重绘的阴影指令，不是像素缓存；没有本项目实测优势 |
| 按显示文本缓存 Image | 采用；阴影、描边和普通文字复用像素，后续按位置绘制图像；需要 DPI、像素预算和资源释放 |
| 直接替换 canvas_danmaku | 本轮不采用；需重做点播确认时钟、seek/旧事件隔离、倍速独立动画和窗口保留验收 |
| 每条 Widget/Layer 或自定义 GPU/字形图集 | 未实施；前者增加组件/合成数量，后者增加图集管理与多语言字体兼容成本；当前测量未证明需要 |

直接接入 0.3.3 能用于一般直播弹幕，但本项目仍要保留下列适配；与其形成两套调度所有者，本轮沿用已有控制器并借鉴其绘制方法。MIT 许可不是替换的阻碍。

| 本项目契约 | 直接接入需要的工作 |
| --- | --- |
| 点播按确认位置触发、seek 重建、暂停/缓冲冻结、动画速度独立于倍速 | 库接收立即添加的内容，没有媒体时间窗/确认 seek 契约；应用另写调度、清空与重放适配 |
| 普通弹幕逐项字号、行距为 0–100 逻辑像素、播放器顶部/底部保留区 | 普通内容使用全局字号与行高倍率，需要包装或扩展以保持现有语义 |
| 500 待处理/120 活动/每帧 32 项准备/32 MiB 图像预算 | 库未提供对应队列、像素和每帧准备上限，需要额外限流及内存策略 |
| 默认模糊阴影、跨窗口保留已消费 ID 与活动年龄 | 默认描边及库内状态与现有实现不同，需要扩展并重跑兼容回归 |

## 实现与约束

生产修改位于 [弹幕包](../../packages/bili_danmaku/lib/bili_danmaku.dart)。应用的网络/解码/账号边界没有变化。

1. 点播时间窗更新只验证、排序、裁剪、维护已消费 ID 和活动身份；文字准备移至 `frame` 的到期候选。点播与直播每帧最多准备 32 项；过期、合并和已有容量满的项先跳过，原来的 500 项队列和 120 项活动安全上限继续生效。直播未处理项保留收到时间并在超龄后丢弃，点播按媒体年龄判断可见性。
2. 轨道占用按模式/行建立索引，只检查同一轨道，仍验证滚动尾部间距和追尾。行高来自实际候选/活动文字的测量；活动期间只增不减，大文字到达时重新投影并裁去不可用行，保留其他项的身份和动画年龄，全部空闲后允许缩小。
3. 点播暂停 seek 的剩余到期候选允许继续有限帧准备，两个时钟保持冻结，队列处理完就停止额外帧。播放、缓冲、样本过期和倍速行为保持原契约。
4. 阴影、描边和普通文字只在实际绘制时按 DPR 生成图像，后续移动图像；描边段落只在需要绘制时创建。依据 Flutter 的 [Picture.toImageSync 契约](https://api.flutter.dev/flutter/dart-ui/Picture/toImageSync.html)，图像句柄同步返回，实际栅格化异步进行，GPU 可用时驻留 GPU。
5. 布局最多 256 项；每控制器缓存的 RGBA 像素预算 32 MiB，单图两个维度均不超过 4096 物理像素。预算是图像字节估算，不能等同实际 GPU 驱动分配。优先淘汰非活动图像，活动集超过预算时溢出项直接绘制，避免缓存互相挤出并反复生成。DPR 改变、样式变化、LRU 和控制器销毁均释放旧图像；零尺寸、超长文本等沿用原绘制/调度边界。

## Windows Profile 对照

[可复现入口](../../tool/validation/danmaku_performance_probe.dart) 使用普通应用 binding、真实 Overlay 和原生 `FrameTiming`。同一台 Ryzen 7 7700、相同工具链与视口分别构建基线/修复版本；实际视口 1264×681、DPR 1。没有视频解码、网络或真实账号。

三种效果分别生成 500 条含中文、英文、emoji 的唯一文本，字号 24/36，混合滚动/顶部/底部。同步调用测量先预热五次再采样三十次。渲染场景预热两秒后采样六秒：每 250 ms 更新点播窗口或加入 500 条直播消息，以反复触发热路径。这是受控高负载场景；生产点播通常每 15 秒换窗口，分段加载/设置变化也触发刷新。

新版直播调度的单次测量只准备最多 32 个候选，其余由后续帧完成，不代表在 2 ms 内完整处理 500 条。计时器内的窗口替换另用 Stopwatch 测量，不能只看 `FrameTiming.buildDuration` 来估算其同步耗时。

相同输入参数的基线与最终实现结果如下。最终加入三种样式的图像缓存与活动工作集保护。

| 指标（P95） | 原实现 | 最终实现 |
| --- | ---: | ---: |
| 点播 500 条窗口替换，阴影 | 22.327 ms | 0.130 ms |
| 直播突发首帧调度，阴影 | 42.827 ms | 1.769 ms |
| 点播 UI / raster，阴影 | 4.118 / 55.773 ms | 0.262 / 0.598 ms |
| 直播 UI / raster，阴影 | 60.921 / 66.670 ms | 2.884 / 1.111 ms |
| 直播 UI，描边 / 无效果 | 66.714 / 44.219 ms | 2.353 / 2.818 ms |
| 直播 raster，描边 / 无效果 | 4.733 / 2.980 ms | 0.924 / 1.097 ms |
| UI 或 raster 超过 16.67 ms，点播 / 直播阴影 | 128/128、108/108 帧 | 0/1074、0/461 帧 |

最终六组场景均没有采样帧超出 16.67 ms。可见数量峰值为点播 42–43、直播 60，没有通过清空弹幕或关闭阴影达成性能变化。图像 RGBA 估算峰值为点播约 11.46 MiB、直播约 10.55 MiB，均低于 32 MiB 预算。帧数包含原生异步批量回报；只用于这次样本的超预算统计，不从它计算显示刷新率。

原始 JSON 和构建/检查日志在 Git 忽略目录 `artifacts/danmaku-performance/` 及 `artifacts/danmaku-performance-*.log`。`baseline.json` 为原实现，`fixed.json` 为首轮阴影优化，`fixed-final.json` 验证活动图像保护，`fixed-raster.json` 为最终三种样式的复测。

另运行 `canvas_danmaku` 0.3.3 的原生对照，同一个 Profile 进程依次显示库和自建 Overlay。两者统一字号 24、正常字重、8 秒滚动/4 秒固定、无每秒限流，每 250 ms 加入 500 条唯一文本，关闭库的 massiveMode 和 safeArea。库用行高倍率近似 5 像素空白，自建按实际布局高度加 5 像素，因此两者活动数量不同。记录 `canvas-comparison-final.json`：

| 实现/效果 | 添加 500 条 P95 | UI P95 | raster P95 | 活动峰值 | 图像像素估算峰值 |
| --- | ---: | ---: | ---: | ---: | ---: |
| canvas_danmaku 0.3.3，普通 | 26.924 ms | 0.226 ms | 1.203 ms | 115 | 9.82 MiB |
| 自建，普通 | 0.674 ms | 2.067 ms | 0.893 ms | 90 | 12.95 MiB |
| canvas_danmaku 0.3.3，描边 | 26.913 ms | 0.172 ms | 0.973 ms | 115 | 10.46 MiB |
| 自建，描边 | 0.613 ms | 2.155 ms | 0.806 ms | 90 | 12.95 MiB |

库把文字准备集中在同步 `addDanmaku`，自建 `add` 只入队，再在后续帧分摊准备。上述添加耗时位于 Timer 回调，不能用低 `FrameTiming.buildDuration` 掩盖；库四舍五入约 27 ms 的突发添加仍阻塞 UI isolate。自建的低添加耗时也不代表全部准备完成。四组采样帧均未超过 16.67 ms，但数量/轨道规则不同，不用这张表宣称相同可见数量下谁的纯绘制更快。自建缓存同时保留近期已离屏图像，库主要保留活动项，内存峰值也不能作等量比较。

复现当前实现：

```powershell
flutter build windows --profile --no-pub -t tool/validation/danmaku_performance_probe.dart
& ./build/windows/x64/runner/Profile/bilisail.exe
# 完成后恢复产品入口
flutter build windows --profile --no-pub -t lib/main.dart
```

## 行为与平台验收

新增回归覆盖未来事件不占布局缓存、刷新复用活动布局、单帧准备量、暂停 seek 完成准备、直播过期积压不布局、大文字到达保留原活动身份、三种效果缓存与直接绘制在 DPR 1/2 的像素一致性（测试字体、整数位置）、图像复用/DPR/样式/容量释放，以及活动图像工作集超预算时不循环淘汰。既有时钟、行距 0/5、自定义字体大小、全屏/控件、seek、重复合并和容量回归继续执行。

- `tool/check.ps1 -SkipPub`：格式与分析全部通过；根应用 1568、API 336、播放器 32、弹幕 72、合并包 2，共 2010 项测试通过。合并包另外 7 项原生测试因未设置 `BILI_MUX_LIBRARY` 按脚本跳过，与本轮弹幕无关。日志为 `artifacts/danmaku-performance-full-check-verified.log`。
- `flutter build windows --profile --no-pub -t lib/main.dart`：通过，已将探测入口恢复为正常应用入口。日志为 `artifacts/danmaku-performance-main-build-verified.log`。
- 修改文档的 304 个本地链接和 `git diff --check` 通过；依赖与锁文件没有变化。

验证期间一次并行运行应用构建与根测试争用了 `build/native_assets/windows/sqlite3.dll`，导致该次构建和 17 项 SQLite 测试失败。停止并行后按完整检查 → 应用构建顺序重跑，全部通过；没有为该工具竞争修改生产实现。原失败日志保留为 `danmaku-performance-full-check-final.log` / `danmaku-performance-main-build.log`。

本轮性能结论限定在 Windows 原生 Profile 的模拟弹幕，未验证真实密集视频与视频解码共同运行，也未构建/运行 Android 或 macOS，不能外推低端移动设备的帧耗时。高 DPI、超长文本或活动集超过像素预算时会回退直接绘制；这些压力条件需要相应设备补测。
