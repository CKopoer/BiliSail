# Android 4K60 H.264：2 倍速与长按切换

日期：2026-11-06（Asia/Shanghai）。承接[上一轮编码对照](android-4k60-codecs-2026-11-05.md)，按用户后续范围只报告 **H.264**。源码基线为 `9c1ea66932c4632acc62be01941913abd4eda5e5`；本轮只扩展验证工具，没有修改产品播放链路、原生依赖、弹幕策略或用户设置。

## 结论

- 本机 H.264 4K60 在 2 倍速下确实按约 2.0 秒媒体时间／秒墙钟推进，实际创建 `c2.qti.avc.decoder`。11 个正式场景的 `decoder-drop-count` 增量均为 0，无缓冲或探针错误。
- **不能给出“2 倍速始终流畅”的结论。** 首轮弹幕＋控件组约 120fps、视频掉帧 0；后续完整播放面板固定 2 倍速仅约 89fps 合成呈现，30 秒增加 930 个 `frame-drop-count`。不同运行状态之间有明显差异。
- **长按切换本身均能正确进入和恢复倍速，但伴随输出掉帧及短暂时钟偏差。** 共 34 次长按／松手、68 次速率转换，均观察到 1.0→2.0→1.0。短长按和快速反复切换每组 30 秒增加 368–418 个视频掉帧，50ms 观测中的最大后端 `avsync` 绝对值约 546ms，主要峰值出现在松手附近。该数值不是测得的物理屏幕／扬声器不同步时长，也不能解释为画面冻结了 546ms。
- 当前线索优先指向**视频输出、Flutter 合成及提交等待，以及倍速转换时的后端时钟衔接**。没有发现手势无法释放或速率命令长期排队；没有将问题定性为硬解芯片算力不足，也没有证明某一个音频缓冲或渲染选项就是根因。

## 条件与方法

设备为同一台 Xiaomi 13（SM8550／骁龙 8 Gen 2、Android 16），系统构建 `Xiaomi/fuxi/fuxi:16/BP2A.250605.031.A3/OS3.0.309.0.WMCCNXM:user/release-keys`。使用 Flutter 3.47.6／Dart 3.13.5 的 Android arm64 **Profile/AOT** 开发测试包 `dev.bilisail.bilisail.test`，版本 1.2.6／12607。Debug 仅验证热重载，不进入性能结论。

素材继续使用 [Blender 官方 Big Buck Bunny Sunflower](https://download.blender.org/demo/movies/BBB/bbb_sunflower_2160p_60fps_normal.mp4.zip) 的公开 SDR 片段（© 2008 Blender Foundation / www.bigbuckbunny.org，[CC BY 3.0](https://peach.blender.org/about/)）。沿用[制备脚本](../../tool/validation/prepare_4k60_codec_samples.ps1)产生的 90 秒 H.264 High 8-bit 视频及独立 AAC 音轨；重新核对手机文件哈希与本地 manifest。视频为 3840×2160、60fps、约 7.7Mbps。没有使用 B 站会员资源或真实账号。

- 复用生产 `PlaybackSession`、`MediaKitEngine`、`VideoSurface`、`PlaybackPanel`。本地 DASH 分轨播放，音频实际解码，音量 0。解码和原生输出纹理都是 3840×2160；手机屏幕为 2400×1080，不能称为原生 4K 屏幕验收。
- 每场重新定位到 0 秒，预热 8 秒，再采样 30 秒；共 11 场、约 **330 秒**正式采样。不同倍速的媒体覆盖区间不同，不是同一组视频帧的画质或能耗比较。
- 对照包括纯 `VideoSurface`、完整面板隐藏控件和弹幕、完整面板叠加弹幕及持续可见控件。叠加设置沿用 Android 默认：字号比例 0.6、区域 0.5、透明度 0.8，每秒输入 20 条，80% 滚动／20% 固定，保留生产容量限制。
- 长按由主机经 Android `input touchscreen motionevent DOWN/UP` 注入，经过生产手势识别器和快捷键协调器；没有直接调用临时倍速方法代替手势。根 `Listener` 记录应用收到触摸的单调时间。默认长按门槛为 400ms、目标倍速 2.0，基线为 1.0。
- 两种叠加条件各执行 6 次普通长按（目标按住 1500ms、间隔 1200ms）、10 次快速长按（650ms／650ms），以及 1 次长按约 18 秒。Android 注入命令带来约几十毫秒的实际松手延迟，机器数据保留收到 DOWN／UP 的时间。
- 每秒记录完整播放／绘制状态，切换场景另以约 50ms 间隔记录原生掉帧、后端时钟及速率。记录后端速率的延迟有该采样粒度，不代表音频物理输出已经在同一时刻完成切换。
- GPU busy 是整机 KGSL 时间比例；SurfaceFlinger 为应用 Surface 的合成呈现，不等于解码帧率。Flutter raster 计时包含等待，不能当作纯 GPU 运算耗时。保留每场 Perfetto、CPU 样本和原始时间序列。

## 持续播放

| 场景 | GPU busy | 合成呈现 | raster P95 | 30 秒视频／解码掉帧 |
| --- | ---: | ---: | ---: | ---: |
| 首轮 2x，纯 Surface | 44.9% | 109.5fps | 无 Dart 帧口径 | 1／0 |
| 首轮 2x，弹幕＋控件 | 80.3% | 119.9fps | 9.02ms | 0／0 |
| 后续 1x，完整面板隐藏叠加 | 37.5% | 60.3fps | 16.62ms | 0／0 |
| 后续 1x，弹幕＋控件 | 58.3% | 89.0fps | 11.50ms | 0／0 |
| 后续 2x，完整面板隐藏叠加 | 54.4% | 89.0fps | 11.70ms | 930／0 |

首轮 2x 两场的媒体推进约为 2.0，后续固定 2x 也保持 2.0；后者没有因输出掉帧而变成正常速度播放。2x 对 60fps 素材提出约 120 帧／秒的处理需求，不能用“播放进度达到 2x”替代流畅度验证。

后续固定 2x 的 30 秒 trace 中，执行 `eglSwapBuffers` 的 `Thread-8` 约提交 2672 次；与约 89fps 的 Surface 呈现接近。该线程的 `eglSwapBuffers` 累计墙钟约 24.85 秒，raster 的 `QueuePresentKHR` 约 17.57 秒，而 raster 实际运行 CPU 约 7.05 秒。**这些包含等待且存在嵌套，不能相加当作 GPU／CPU 计算时间**；它们支持继续检查输出互操作、队列／fence 与提交节奏，而不是仅优化手势回调或 Dart UI 构建。

首轮和后续组并非受控的频率 A/B。两个 Profile APK 的原生 `.so` 哈希逐项一致，但设备运行状态未锁定：电量从 12% 降至 7%，电池温度由约 32.4°C 升至 38.9°C，所有正式场景 Thermal Status 均为 0；未读取到可用于逐组对齐的 GPU 频率。系统显示模式实读为 120Hz，省电模式为 0，没有修改这些设置。早期约 120fps 与后续约 89fps 的差异，不能单独归因于控件、长按、温度或某个编码器。

## 长按与松手

下表每行均采样约 30 秒；长按过程中穿插 1x 与 2x，故平均呈现率不代表固定 2x 的呈现率。

| 场景 | 次数 | 视频／解码掉帧 | 50ms 观测的最大绝对 avsync |
| --- | ---: | ---: | ---: |
| 普通长按，隐藏叠加 | 6 | 368／0 | 523ms |
| 快速反复，隐藏叠加 | 10 | 388／0 | 477ms |
| 普通长按，弹幕＋控件 | 6 | 393／0 | 546ms |
| 快速反复，弹幕＋控件 | 10 | 418／0 | 500ms |
| 按住约 18 秒，隐藏叠加 | 1 | 569／0 | 168ms |
| 按住约 18 秒，弹幕＋控件 | 1 | 575／0 | 298ms |

34 次长按都完整恢复。按下到观察到 2x 为约 **403–454ms**，包含默认 400ms 长按判定；松手到观察到 1x 为约 **5–49ms**。短长按期间已有连续输出掉帧，松手附近还出现更集中的掉帧和时钟峰值。因此不能把累计掉帧全部算作松手动作，也不能把响应迅速等同于输出平滑。

50ms 位置观测中的最大更新间隔约 264ms；这是后端位置通知口径，不是屏幕画面停留时长。所有正式样本仍处于 playing、无 buffering／seeking、无 Flutter 错误。没有外录扬声器与屏幕，未验收实际听感、蓝牙音频或物理音画同步。

## 复现、检查与恢复

[机器数据](data/android-4k60-h264-2x-hold-2026-11-06.json)保存 11 场摘要、全部场景参数、34 次触摸转换时间、媒体元信息／哈希、实际硬解组件匹配、Perfetto 摘要、APK 身份和原生库哈希。原始数据位于忽略目录：

- `build/validation/android-4k60/codecs_x2_a/`：只采用其中两个已完成的 H.264 场景；用户收窄范围后主动停止，其他编码不进入本文。
- `build/validation/android-4k60/{h264_holds_a,h264_holds_b}/`：长按与补充对照。
- `build/validation/android-4k60-2x/`：配置、构建／检查日志、汇总与重载记录。

构建和运行入口：

```powershell
./tool/build-android-development.ps1 -Mode Release
# 先保留普通 Release 为 build/validation/android-4k60/ordinary-release.apk。
flutter build apk --profile --target-platform android-arm64 --split-per-abi --target tool/validation/android_4k60_probe.dart --android-project-arg=bilisailDevelopmentBuild=true
# 将 Profile APK 保留为 build/validation/android-4k60/probe-profile.apk。
./tool/test-android-4k60.ps1 -DeviceId <adb-id> -ConfigPath <scenario.json> -Label <fresh-label> -UsePreparedApks
python tool/validation/summarize_android_4k60.py <run-folder> --trace-processor <trace_processor_shell.exe> --output <summary.json>
```

场景可在既有字段外指定 `rate`、`seekSeconds`、`holdCycles`、`holdMs`、`gapMs`。长按场景要求 `panel: true`、`rate: 1`；本次配置完整保存在机器数据的 `rows[].scenario` 中。样片放置与许可沿用上一轮记录。

- 根 `tool/check.ps1 -SkipPub` 通过：根应用 4423、bili_api 659、bili_player 148、bili_danmaku 161、bili_mux 5，共 **5396 项**。根应用 13 项、mux 原生 10 项按环境跳过；没有配置 `BILI_MUX_LIBRARY`，不算 mux 原生验证。
- 最终探针格式／静态分析、Python 编译和 collector 的 3 项 HTTP 行为测试通过；PowerShell 语法检查通过。Debug 完成实际 `reloadSources`（success）及 `ext.flutter.reassemble`。
- 两轮 Profile 长按数据均有全部 `phase-end`／`complete`、30 个逐秒样本及约 30 秒有效 CPU trace，无 ring overwrite／丢失统计；原有运行器却在收尾报了 deadline 错误。没有把该错误说成应用失败或把退出码说成通过。运行器现改用单调 Stopwatch、显式完成标志及超时诊断；后续 Debug 与短 Profile 运行均以退出码 0 完成，普通 APK 恢复哈希也通过核对。

- 专项 APK、SHA-256 与模式元信息保存在 `build/development/android-arm64/BiliSail-test-arm64-4k60-h264-hold-{profile,debug}.apk*`。普通 Release 仍为默认日常测试入口。

本轮只覆盖该手机、本地 SDR H.264 样片及上述短时手势。没有增加其他编码、HDR、高码率、网络弱网、其他设备或长期温升的验收结论。下一步若继续定位，应在可对齐的运行状态下隔离 Surface／完整面板与原生输出等待，再对倍速音频时钟转换做受控对照。
