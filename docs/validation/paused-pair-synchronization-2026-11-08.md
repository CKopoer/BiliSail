## 原因与现行行为

旧共享启动门先静音播放，再等音频解码和画面呈现，最后恢复音量。这只能推迟声音，不能阻止视频先推进；仅凭已存在的音频解码参数，也不能确认刚刚 seek 的目标已经加载。

- `finishSynchronizedStartup` 先确认暂停，等待当前目标的音频和视频及输出呈现，再应用用户音量与增益、调用 play。首次起播、暂停后每次继续、seek 后恢复共用此流程。等待期间不预跑、不强制归零音量；预览与用户设置的零音量仍按原语义处理。
- 所有等待保留源代次、意图版本、取消和总 deadline。暂停打开期间收到新 play 时，旧就绪检查不能直接放行新意图；新意图重新确认音频。缓冲事件不能提前撤销双轨等待态，旧进度采样不能改变尚未确认的位置。
- media_kit 在暂停中等待当前 load／seek 的 `PLAYBACK_RESTART` 和实际音频解码参数。mpv 只有两条解码链均到 READY 后才发送该事件；原生视频同步明确使用 `video-sync=audio`。依据：[mpv 播放循环](https://github.com/mpv-player/mpv/blob/master/player/playloop.c)，仅采用事件契约，未复制源码。
- fvp DASH 将原先用后即销毁的音频探针替换为真实音频伴随管线，由同一 `FvpPlayerPort`／engine／会话拥有。视频管线关闭自身音轨，因此只有一个真实音频输出。音频管线保留并使用自己的请求头、描述符、缓冲窗口、速率及用户音量。
- fvp 两轨均暂停定位；视频 seek 完成后，真实音频管线定位到该确认位置并核对结果（最大差 100ms），成功后才允许共同恢复。纯音频 seek 的 SDK 回调确认音频目标帧，不以暂停状态下可能不变化的音频 filter 计数冒充就绪。契约见 [MDK Player API](https://github.com/wang-bin/mdk-sdk/wiki/Player-APIs)。
- 视频通过 MDK 原生 `onSync` 跟随音频原生呈现时钟，回调不跨入 Dart。暂停／seek 持有目标锚点，恢复后先排除旧时钟再跟随真实音频；目标版本隔离旧回调。该时钟不依赖 Dart 定时器估算播放位置。音频停止推进时，视频也等待该时钟。
- 取消 seek 同时退休两条在途原生读取；新目标在原生取消屏障之后再撤销旧 HTTP reader。释放先销毁并等待视频线程退出，再释放时钟状态、音频管线及其描述符。Android worker 仍隔离原生进程，新增音频时钟采样经现有序号校验传回。

自然音频 EOS 会复位 SDK 的音频时钟。原生桥保留最后有效时钟，依据接近片尾的视频位置识别正常结束，仅放行最终视频帧；提前音频 EOS 立即触发原有有界恢复并记录音频时钟中断。直播在暂停中确认已缓存首帧，不发起网络 seek。

单文件及直播继续使用 SDK 内部音视频管线；普通无音轨源与听视频按实际轨道要求等待。原有应用层线路恢复、播放许可与重试预算不变。
