日期：2026-11-14（Asia/Shanghai）。范围：本机正在运行的 Windows Release 日志、共享播放适配层和离线回归；按用户要求不构建、不操作当前播放器，后续由用户构建并实机验证。

`MediaKitBackend` 以前把 SDK error 交给通用 `NativeErrorMonitor`。后者在视频时间线继续推进时清除错误，无法证明音轨仍在输出。`hasDecodedAudio` 来源于声道／采样率元数据，解码失败后这些旧值仍可保留，因此也不能证明恢复。2026-11-12 换源重构已经移除了常驻音频时钟轮询；原生播放器允许另一条轨道继续，最终留下“画面播放、音频失声”的缺口。

本次确定的是现场音频解码错误以及应用漏恢复的路径。现有日志没有原始解码文本、音频包或实际声卡采样，不能进一步断定最初错误由损坏媒体包、线路中断或解码器内部状态中的哪一种引起；也没有证据证明它只发生于 Release。

## 修复

- 新增包内 `NativeAudioErrorMonitor`，只接收 `ad`／`ffmpeg/audio` 的 error／fatal 解码错误。活动播放或 buffering 一旦收到即发出 `nativePlayback` 失败，不等待视频停滞、缓存耗尽或音频时钟采样；通用警告和其他组件错误保留原分类。
- HTTP、超时、连接及 I/O 预读错误直接请求恢复，不再先等待五秒探测旧线路可达。已知时长且同一原生 EOF 事件中的 `cache-end` 未到片尾时也立即恢复；完整缓存的正常 EOF 不重开，避免 SDK 的独立缓冲通知尚未更新时误重试。端点未知则保留有界探测。已经 buffering 且缓存为空的明确读取错误同样立即重试。
- 共享引擎先确认整对音视频暂停，再沿用会话已有的线路／地址刷新、最多三次 native open 和 35 秒准备预算，保留位置、倍速、音量与播放意图；每个原生源的同类错误只请求一次，没有增加另一套重试额度。
- 没有明确错误事件的静默读停滞保留原来的五秒观察与有界可达性探测，避免把正常读缓存回压当作故障。错误事件可升级正在进行的探测，取消旧探测并直接恢复，迟到结果不能再请求第二次恢复。
- 暂停不自动播放；暂停期间发现的音频错误保留到下一次明确播放意图。seek 清除本次音频错误；新源、复用重置、停止和释放销毁监测器，旧源事件沿用现有代次隔离。
- 正常播放无新增定时器、原生属性轮询或高频 Provider 更新。静音预览不安装音频错误监测器。补齐错误分类器对 `decoding` 的识别。

只读核对 [mpv 音频解码错误入口](https://github.com/mpv-player/mpv/blob/master/audio/decode/ad_lavc.c)及 [demuxer-cache-state 语义](https://mpv.io/manual/stable/#command-interface-demuxer-cache-state)：单个坏包也可能产生解码错误，因此立即恢复策略可能比等待原生自行恢复更积极，仍由既有会话预算限制重试。没有复制 mpv 代码、修改个人 fork／Pub 缓存或升级原生依赖。预读恢复的原始实现记录见[预读断流恢复](prefetch-network-recovery-2026-11-14.md)，本次明确错误立即恢复策略覆盖其中先探测再重开的行为。
