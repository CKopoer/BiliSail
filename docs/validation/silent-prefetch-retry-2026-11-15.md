# 有可播缓存时优先静默恢复

日期：2026-11-15（Asia/Shanghai）。按用户后续要求，明确读错、无报错的读取停滞，以及音频／视频解码、硬解与视频输出故障统一使用原生恢复窗口。

## 现场与原则

进程 25592 的 Release 在 22:04:18 收到 `prematureRead / inputOutput`，当时仍有 119.723 秒媒体缓存，3 倍速下约可播 39.9 秒。原修复及时触发 `prefetchReadError` 并从原位置重开，两轨约 0.82 秒后就绪，但打断了已有缓存并出现自动重试提示。

本次原则：有可播缓存且所需音视频轨仍推进时，先保留原播放器，让 mpv／FFmpeg 在同一管线恢复；半窗口用尽或出现实际停帧、断音、buffering 后，再交给已有会话的有界重开。HTTP 的既有原生续读保持不变，见 [FFmpeg HTTP 文档](https://ffmpeg.org/ffmpeg-protocols.html#http)。应用不隐藏已经开始的重开，也不新建代理、字节缓存或第二组播放器。

## 一个半窗口

```text
remainingMedia = buffered - position
silentWait = remainingMedia / playbackRate / 2
```

`buffered` 使用原生事件提供的实际缓存端点，已受既有时长和字节上限共同约束，直接取实际窗口的一半；不另估码率，也不以配置的 120 秒代替实际缓存。例如实际缓存 120 秒、3 倍速时静默等至多 20 秒；字节限制使实际缓存仅剩 8 秒、2 倍速时至多等 2 秒。

- 所有故障入口共用 `NativeBufferRecovery` 的一次等待；重复日志、不同错误叠加及缓存增长不重算截止时间。保存原窗口媒体中点，升速先到中点则提前处理，降速不延长首次计时。
- 明确读错直接进入该等待。静默读停滞保留原先的原生读取活跃性判断：仍在读取却五秒没有缓存增长时开始相同的半窗口。移除应用侧线路可达性探测，避免网络探测把半窗口推后；原生仍自行续读，到期交回会话原有的有限重开预算。
- 等待期间不发布失败、不暂停或重开、不设置会话重试提示。无缓存或已经 buffering 的故障没有静默条件，沿用有界恢复。
- 只有读流故障能由新增至少一秒缓存且两轨实际推进清除。尾包、小幅缓存估计更新、总进度或旧的健康采样不能独自证明恢复；缓存增长不能清除解码／输出故障，后者仍受原半窗口限制。
- 正常 EOF／满缓存 idle 取消没有明确错误的读停滞探测及等待；明确错误不会被 idle／EOF 抹去。暂停、seek、换源、结束及释放取消旧计时与迟到结果，源代次不匹配的样本无效。
- URL 刷新、备用 CDN 和整组恢复继续使用原会话重试与准备预算，没有增加 native open 次数。

## 实际停帧与断音

仅在故障等待期间，每 500ms 做一次有超时的低频采样，平时不查询原生时钟。音频使用 `audio-pts`，视频使用锁定 mpv 在视频活动时跟随视频的 `time-pos`，并检查 `video-format` 及双轨的 `avsync` 有效性。锁定源码 `player/playloop.c:update_playback_time` 在视频停止活动时会让总时钟回退到音频，所以不能只看界面 position；锁定 SDK 没有独立 `video-pts` 属性。[mpv 属性说明](https://mpv.io/manual/stable/#properties-audio-pts)

任一所需轨道持续两秒不推进或没有可用时钟，便停止等待并交给现有恢复，不等整段缓存耗尽。每个属性查询有 400ms 超时，整次采样有一秒上限；迟到结果与旧源隔离。听视频只检查音频，明确无音轨的预览只检查视频。软件解码 error 也接入同一策略；普通 warning、硬解建议和正常 fallback 不因本次改动变成失败。

该判断依据原生输出时钟与轨道状态，不能证明扬声器、GPU 驱动或屏幕最终呈现始终正常；设备静音、系统音量和静态画面也不属于断音／停帧证据。

## 缓存复用边界

静默期间保留同一原生播放器及其压缩包缓存，给原生恢复机会；不主动重置解码器。本项目 DASH 是同一个 mpv EDL 的两轨，已有整组重开会释放原生缓存，不能保证此时无缝续上。`audio-reload`／`video-reload` 面向外部轨道，变更 `hwdec` 也可能 seek，不能作为通用的保缓存解码器重置接口，见 [mpv reload](https://mpv.io/manual/stable/#command-interface-video-reload)。
